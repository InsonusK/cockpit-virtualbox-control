# Постановка: миграция VirtualBox Cockpit-плагина на Alpine.js

## Контекст

Существует рабочий Cockpit-плагин для управления VirtualBox VM через `VBoxManage`
(вызовы идут через `cockpit.spawn()`). Текущая реализация — vanilla JS,
ручная сборка DOM (`document.createElement` / `innerHTML`) в отдельных
файлах-компонентах.

Разработка ведётся в `~/.local/share/cockpit/virtualbox/` — это стандартное
место Cockpit для пользовательских пакетов в разработке: правишь файл,
жмёшь Ctrl+Shift+R в браузере, видишь результат сразу, без пересборки и
без перезапуска сервисов.

Проект будет вестись в GitHub-репозитории. Деплой на серверы через Ansible
настраивается отдельно и не входит в объём этой задачи — агенту не нужно
учитывать пути `/usr/share/cockpit/...` или сам процесс деплоя. Единственное,
что важно для совместимости с будущим Ansible-деплоем, — итоговая структура
директорий репозитория (см. ниже), чтобы тесты не оказались среди файлов,
которые в итоге копируются на сервер как Cockpit-пакет.

### Текущая структура файлов (на момент начала миграции)

```
app.js                    — точка входа, верхнеуровневый оркестратор
client/
├── parser.js              — чистые функции парсинга вывода VBoxManage
└── vboxClient.js           — обёртки над cockpit.spawn(): listDvds(), vmInfo(guid) и т.д.
components/
├── utils.js
├── vmCard.js
└── ... другие файлы рендеринга (сборка DOM вручную)
manifest.json
index.html
style.css
```

## Цель миграции

Перейти на Alpine.js для управления состоянием интерфейса (раскрытие карточек
VM, детальные панели, в перспективе — формы редактирования), сохранив принцип
"без build-шага" — Alpine подключается статическим файлом, без npm/webpack/vite.

Разметка каждого компонента выносится в отдельный HTML-фрагмент (вариант с
подгрузкой через `fetch`), а не остаётся одним большим `index.html` — так
JS-логика и разметка компонента лежат рядом парой файлов и проще ревьюятся
по отдельности.

## Причина

Функциональность плагина растёт в сторону "полного контроля над VM"
(развёрнутые инфо-панели, в перспективе — редактирование сети/дисков).
Ручная сборка DOM в `components/` на этом масштабе становится неудобной.
Alpine даёт декларативную реактивность без потери текущего цикла разработки.

React/Vue/Angular осознанно не рассматриваются — избыточны для масштаба
задачи (6 VM, редкие изменения, один разработчик) и требуют build-пайплайна,
который сломает текущий цикл "правка → Ctrl+Shift+R".

## Требования к результату

### Функциональные (сохранить без регрессий)
- Список VM с состоянием (running/paused/off) и обновлением по кнопке.
- Действия: start (headless/GUI), pause/resume, ACPI shutdown, force off.
- Просмотр и управление снапшотами (список, создание, восстановление).
- Разворачиваемая инфо-панель по клику на карточку VM (уже реализовано,
  перенести на `x-data`/`x-show`).

### Архитектурные

1. Alpine.js подключается локальным файлом (скачать `alpine.min.js`,
   положить в `vendor/`, коммитить в репозиторий), не через CDN — плагин
   должен работать без доступа сервера в интернет.

2. Сохранить разделение `client/` (данные и побочные эффекты) и
   `components/` (представление), но пересмотреть роль обоих слоёв
   представления:
   - `client/parser.js` — остаётся как есть: чистые функции парсинга,
     без обращений к `cockpit`/`document`. Единственный слой, который
     покрывается unit-тестами.
   - `client/vboxClient.js` — остаётся как есть: обёртки над
     `cockpit.spawn()`, без DOM-логики.
   - `components/*.js` — переписать так, чтобы они отдавали
     `Alpine.data(...)`-объекты (состояние + методы), без единой строки
     HTML внутри JS.
   - `partials/*.html` — новая директория. Каждому файлу из `components/`
     соответствует одноимённый HTML-фрагмент с разметкой этого компонента
     (директивы `x-data`, `x-show`, `x-for`, `@click` и т.д.). Пример
     парного соответствия: `components/vmCard.js` ↔ `partials/vm-card.html`.
   - `app.js` остаётся оркестратором: загружает партиалы, инициализирует
     Alpine, регистрирует компоненты из `components/`, стартует Alpine
     после того, как вся разметка вставлена в DOM.

3. Механизм подгрузки партиалов:
   - `index.html` — только каркас (`<div id="app">`, подключение `alpine.min.js`,
     `app.js` как `type="module"`), без разметки конкретных компонентов.
   - Партиалы подгружаются через `fetch()` и вставляются в DOM
     **до вызова `Alpine.start()`** — это важно: Alpine автоматически
     инициализирует директивы на уже существующих в DOM узлах при старте,
     и если весь порядок соблюдён (сначала все `fetch`, потом `Alpine.start()`),
     не нужно вручную дёргать `Alpine.initTree()` для динамически
     вставленных фрагментов. Не усложнять эту цепочку без необходимости.
   - Вынести сам механизм подгрузки в переиспользуемую функцию, например
     `components/loadPartial.js` (`loadPartial(path, targetSelector)`),
     а не дублировать `fetch`-логику в каждом компоненте.

4. Все аргументы в `cockpit.spawn()` — только в виде массива элементов,
   никогда не собирать shell-строку конкатенацией. Жёсткое требование,
   актуально уже сейчас и станет критичным при появлении форм с
   пользовательским вводом.

### Тестирование

- `client/parser.js` не имеет зависимостей от `cockpit`/`document` — тестируется
  в Node напрямую через встроенный `node:test` (без Jest/Vitest).
- Покрыть happy path + граничные случаи (пустой вывод, VM без снапшотов,
  неожиданный формат вывода `VBoxManage`).
- `client/vboxClient.js`, `components/*`, `partials/*` и механизм подгрузки —
  unit-тестами не покрывать, не соразмерно ценности для текущего масштаба
  проекта.

## Итоговая структура репозитория

Ключевой момент: то, что реально становится Cockpit-пакетом (и в будущем
копируется Ansible-плейбуком на сервер), — это только содержимое `src/`.
Тесты и прочие dev-артефакты в `src/` не попадают, поэтому деплой пакета —
это всегда "скопировать `src/` целиком", без исключений и фильтров.

```
repo-root/
├── src/                        <- это и есть Cockpit-пакет целиком
│   ├── manifest.json
│   ├── index.html               <- только каркас, без разметки компонентов
│   ├── style.css
│   ├── app.js                   <- оркестратор: загрузка partials + запуск Alpine
│   ├── vendor/
│   │   └── alpine.min.js
│   ├── client/
│   │   ├── parser.js
│   │   └── vboxClient.js
│   ├── components/
│   │   ├── loadPartial.js
│   │   ├── utils.js
│   │   ├── vmCard.js
│   │   └── ...
│   └── partials/
│       ├── vm-card.html         <- парный файл к components/vmCard.js
│       ├── snapshot-modal.html
│       └── ...
├── tests/
│   └── parser.test.js          <- импортирует из ../src/client/parser.js
└── README.md
```

Локально для разработки `src/` разворачивается в `~/.local/share/cockpit/virtualbox`
(симлинком либо просто рабочей копией — на усмотрение агента, лишь бы
сохранялся быстрый цикл правки без пересборки).

## Не входит в объём этой задачи
- Формы редактирования сети/дисков/ресурсов VM — следующий этап.
- Ansible-плейбук и деплой на `/usr/share/cockpit/` — отдельная задача,
  для неё важна только итоговая структура `src/`/`tests/` выше.
- CI-пайплайн для автозапуска тестов — по желанию, не блокирует миграцию.

## Definition of done
- Все текущие функции работают идентично после миграции (проверить вручную
  по каждому пункту из раздела "Функциональные").
- В `src/` нет `node_modules`, package-lock и прочих build-артефактов —
  только статические файлы, которые браузер отдаёт как есть.
- Каждый файл в `components/*.js` (кроме служебных вроде `loadPartial.js`,
  `utils.js`) имеет парный `partials/*.html` с его разметкой.
- `node --test tests/` проходит без ошибок.
- Во всех местах `cockpit.spawn()` аргументы — массивы, без конкатенации
  строк с пользовательским/динамическим вводом.
